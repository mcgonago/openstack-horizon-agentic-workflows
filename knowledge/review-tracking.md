# Gerrit Review Tracking — Knowledge Reference

This document provides the data model and API reference for tracking OpenDev
Gerrit review conversations. It is the primary knowledge source for the
`/review-tracker` skill.

## Gerrit REST API Endpoints

### Base URL

```
https://review.opendev.org
```

All Gerrit REST API responses have a `)]}' ` XSSI protection prefix on the
first line. Strip it before parsing JSON:

```bash
curl -s "https://review.opendev.org/changes/977939/detail" | tail -n +2 | python3 -m json.tool
```

### Review Detail

```
GET /changes/{change-id}/detail?o=DETAILED_LABELS&o=CURRENT_REVISION&o=MESSAGES
```

Returns the full change object. Key fields:

| Field | Type | Description |
|-------|------|-------------|
| `subject` | string | Commit message first line |
| `owner.name` | string | Change author |
| `status` | string | NEW, MERGED, ABANDONED |
| `updated` | timestamp | Last activity timestamp (use for recheck early exit) |
| `revisions` | map | Patchset data; current revision has `_number` for the latest PS |
| `labels.Verified.all[]` | array | Zuul CI votes (+1 pass, -1 fail) |
| `labels.Code-Review.all[]` | array | Human reviewer votes (-2 to +2) |
| `labels.Workflow.all[]` | array | Core reviewer approval (+1 to merge) |
| `messages[]` | array | Timeline of patchset uploads, CI results, rechecks |

Each message has `date`, `author.name`, `message`, and optionally `tag`
(e.g., `autogenerated:gerrit:newPatchSet`).

### Inline Comments

```
GET /changes/{change-id}/comments
```

Returns a map of `{filepath: [comment]}`. Each comment object:

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique comment identifier |
| `author.name` | string | Commenter name |
| `author.username` | string | Commenter username |
| `updated` | timestamp | Comment timestamp |
| `message` | string | Comment content |
| `line` | int | Line number (0 for file-level comments) |
| `patch_set` | int | Which patchset the comment was made on |
| `unresolved` | boolean | Whether the comment thread is unresolved |
| `in_reply_to` | string | Parent comment ID (for threading) |

Special file paths:
- `/PATCHSET_LEVEL` — patchset-level comments (not attached to a specific file)
- `/COMMIT_MSG` — comments on the commit message itself

## Comment Data Model

### Reply Chains

Comments form reply chains via the `in_reply_to` field. A root comment has
no `in_reply_to`. All replies to a root comment share the same thread.

To reconstruct a thread:
1. Find root comments (no `in_reply_to`)
2. For each root, collect all comments whose `in_reply_to` chain leads back to it
3. Sort by `updated` timestamp within each thread

### File + Line Grouping

Multiple root comments on the same file and line are separate threads
(different topics at the same location). Do not merge them unless they
share a reply chain.

### Resolution Status

The `unresolved` field on the **latest** comment in a thread determines
the thread's resolution status:
- `unresolved: false` → thread is RESOLVED
- `unresolved: true` → thread is still open

A reply that says "Done" does not automatically resolve the thread on Gerrit
unless the replier explicitly clicked "Resolved". Always check the API field.

## Labels and Voting System

| Label | Who Sets It | Values | Meaning |
|-------|-------------|--------|---------|
| `Verified` | Zuul CI | +1, -1 | CI pass/fail (resets on new patchset) |
| `Code-Review` | Human reviewers | -2 to +2 | Code quality assessment |
| `Workflow` | Core reviewers | +1 | Approve for merge |
| `Review-Priority` | Anyone | 0-2 | Optional prioritization |

### Vote Lifecycle

- `Verified` resets on every new patchset (Zuul must re-run)
- `Code-Review` votes may carry over across patchsets (depends on Gerrit config)
- `Workflow+1` is the final gate — only core reviewers can set it

## Patchset Lifecycle

- Each `git push` to a review creates a new patchset
- Comments are made on a specific patchset but remain visible on all patchsets
- A new patchset may address reviewer feedback from earlier patchsets
- The `messages` array in the detail response tracks patchset uploads with
  `tag: "autogenerated:gerrit:newPatchSet"`

## Thread ID Convention

The `/review-tracker` skill assigns each thread a tracking ID:

```
CMT-{AUTHOR_SHORT}-{N}
```

Where:
- `AUTHOR_SHORT` is a short code derived from the author's name (e.g., OWN for Owen, JAN for Jan)
- `N` is a sequential number per author

Examples: `CMT-OWN-1`, `CMT-JAN-3`, `CMT-PL-2` (PL = patchset-level)

For CI/automation comments, use the automation name: `CMT-ZUUL-1`, `CMT-GERRIT-1`
